# Architecture

## Purpose

This platform demonstrates a serverless, event-driven pattern for operational events generated by distributed field environments.

Typical events include connectivity degradation, equipment alerts, telemetry conditions, and operational threshold breaches.

+--------------------------+

| Systems                  |

## Component Responsibilities

### API Gateway

Provides the HTTPS entry point:

```text
POST /events
```

### Event Ingestion Lambda

The ingestion handler:

1. Parses the request.
2. Validates it with Pydantic.
3. Generates a UUID.
4. Generates a UTC timestamp.
5. Writes the event to DynamoDB.
6. Returns the event ID.

### OperationalEvent Model

Required fields:

```text
site_id
event_type
severity
message
```

Length constraints are applied to prevent empty or excessively large values.

### DynamoDB

DynamoDB provides persistent event storage.

Primary key:

```text
event_id
```

The table uses `PAY_PER_REQUEST` billing and server-side encryption.

### DynamoDB Streams

The table stream is configured with:

```text
NEW_AND_OLD_IMAGES
```

The stream creates an asynchronous boundary between persistence and downstream processing.

### Stream Processor Lambda

The stream processor receives DynamoDB Stream batches, currently processes `INSERT` events, extracts `NewImage`, logs the event, and reports the processed-record count.

This is deliberately a baseline consumer that can later be extended to trigger alerting, routing, analytics, or incident management.

### CloudWatch

CloudWatch Logs provides operational visibility for Lambda invocations and stream processing.

## Event-Driven Characteristics

The architecture follows:

```text
Producer
   |
   v
API
   |
   v
Persistent Event
   |
   v
DynamoDB Stream
   |
   v
Consumer
```

The API does not wait for the downstream processor.

This allows additional consumers to be introduced without changing the ingestion contract.

## Near-Real-Time Processing

The current design can support near-real-time operational processing:

```text
Connectivity Alert
       |
       v
API Gateway
       |
       v
Lambda
       |
       v
DynamoDB
       |
       v
DynamoDB Stream
       |
       v
Stream Processor
       +----> Alerting
       +----> EventBridge
       +----> Incident Management
       +----> Analytics
       +----> Notifications
```

The correct architectural description is **near-real-time event processing**. The implementation is not intended to represent a high-throughput streaming platform such as Kafka or Kinesis.

## Security

Lambda functions use dedicated IAM roles. The ingestion function is granted the DynamoDB permissions required for its workload, plus CloudWatch logging permissions.

DynamoDB encryption is enabled and API traffic enters through HTTPS.

## Scalability

API Gateway, Lambda, and DynamoDB are managed AWS services designed to scale with workload.

DynamoDB on-demand capacity is suitable for variable event traffic without manually provisioning capacity.

## Reliability

The ingestion and downstream processing paths are decoupled.

Future reliability enhancements include retries, dead-letter handling, idempotency, partial batch failure handling, and CloudWatch alarms.
